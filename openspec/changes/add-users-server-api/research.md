# Research: Users server API (BR-USERS v4.0, server side only)

## Research status

- **Change:** `add-users-server-api`
- **Confidence:** Medium — the current server surface, its shared contracts, and the MongoDB/Express behaviors that constrain the requested endpoints are all verified from installed code and primary documentation; confidence is held below high because operator identity and audit behavior depend on an authentication layer that does not exist anywhere in the repository.
- **Blocking unknowns:** 3 — the identity of the operator (U-002), whether `users` may hold personal data at all given standing project instructions (D-001), and whether the shared error/response contracts may be widened (D-002).

## Executive summary

The request is to build the server half of BR-USERS v4.0: `GET /api/users`, `GET /api/users/:userId`, `PATCH /api/users/:userId`, `DELETE /api/users/:userId`, with server-side pagination, search, filtering, sorting, global email uniqueness, soft delete (archive), optimistic concurrency, and a machine-readable error contract.

Verified current state: the server has no `users` model, no `users` route, no authentication, no operator identity, no audit storage, and no rate limiting (F-001, F-002). The two existing feature modules (`directory`, `events`) establish a strong, spec-backed house contract that the PRD partially contradicts: the shared error envelope carries exactly four codes and exactly `{ error: { code, message } }` (F-003), and collection reads return one named array rather than `{ items, pagination }` (F-004). The PRD needs at least eight new error codes, a `field` member, three new status classes (401/403/429), and a paginated envelope — so this change necessarily amends the `api-foundation` capability, not just adds a `users` one.

The highest-value technical findings are the ones that will silently produce wrong behavior if later artifacts assume the obvious implementation: `express.json()` as configured does not parse `application/merge-patch+json`, so a PATCH sent with the PRD's recommended content type arrives with `req.body === undefined` (F-005); MongoDB sorts `null` *first* ascending, so `NULLS LAST` for `lastLoginAt` is not expressible with a plain sort (F-010); `status` ascending must be `active, inactive, blocked`, which is not the collation order of those strings (F-011); `$regex` is not collation-aware and its `i` flag is ASCII-only by default under PCRE2, so Cyrillic case-insensitive search does not work the way the existing directory search implies (F-012, F-013); and a two-field `$or` regex over `firstName`/`lastName` — the existing house pattern — cannot satisfy `AC-USR-007` (`anna smith`) at all (F-014).

Recommended direction: implement a self-contained `users` module whose stored document carries pre-normalized derived keys (email, name, phone, and an explicit status rank) so that filtering, search, and every required ordering are index-servable and deterministic. Main risk: derived search/sort keys drifting from the displayed fields when a write path bypasses normalization.

## Input and scope

### Explicit requirements

Server-side realization of `docs/prd/release 1.0.0/usersPage/usersPage.md` (BR-USERS v4.0), specifically:

- **Model and identity** — REQ-USR-001 to REQ-USR-003: immutable id and identifier-based API operations.
- **Email rules** — REQ-USR-005 to REQ-USR-007: global uniqueness on `emailNormalized`, archived records keep reserving the address (`409 EMAIL_TAKEN_BY_ARCHIVED_USER`), normalization is trim + lowercase only.
- **Status and archival** — REQ-USR-008 to REQ-USR-011: closed lowercase status set, `archived` is not a status, archive sets `archivedAt` and preserves `status`, no physical deletion, references survive, archive is not privacy erasure.
- **List endpoint** — REQ-USR-018 to REQ-USR-027, REQ-USR-034, REQ-USR-039, REQ-USR-083: archived excluded, server-side pagination (`20|50|100`, default 20, max 100) with the `{ items, pagination }` body, `400` for invalid pagination or unknown sort/status values, deterministic default order `lastName, firstName, id`, sortable First Name / Last Name / Status / Last Login, status ascending order `active, inactive, blocked`, `lastLoginAt` nulls last, Unicode/Cyrillic-correct stable server collation, search across first/last/full name, email, phone, multi-value status filter, explicit response whitelist without `version`.
- **Phone** — REQ-USR-030 to REQ-USR-033, REQ-USR-052: E.164 storage, parsing tolerant of formatting characters, deployment default region for national-format input, extension stored separately and never merged into E.164, phone search normalizes both sides.
- **Detail endpoint** — REQ-USR-046 to REQ-USR-048: `GET /api/users/:userId` returns archived records too (with `archivedAt`), an unknown id returns `404`, and the full `UserDto` includes `version`.
- **Update endpoint** — REQ-USR-050 to REQ-USR-062: RFC 7396 merge-patch semantics including recursive address merge and `null`-means-remove, `Content-Type: application/merge-patch+json` recommended, name/email/address/phone validation with NFC normalization, `400 NO_CHANGES_SUBMITTED`, `400 UNKNOWN_FIELD`, `409 EMAIL_ALREADY_EXISTS`.
- **Concurrency and archive** — REQ-USR-060, REQ-USR-061, REQ-USR-067 to REQ-USR-071: client-supplied `version` guard with `409 USER_VERSION_CONFLICT` and `version + 1` on success, `409 USER_ARCHIVED` for a patch against an archived record, `409 CANNOT_ARCHIVE_SELF`, `409 CANNOT_ARCHIVE_LAST_ADMINISTRATIVE_USER`, `DELETE` returns `204` and is idempotent, archive deliberately ignores `version`.
- **Cross-cutting** — REQ-USR-040 (ISO 8601 UTC on the wire), REQ-USR-042 (sensitive-field whitelist, never `emailNormalized`), REQ-USR-072/073 (error envelope and status semantics), REQ-USR-081 (auditability), REQ-USR-082 (<500 ms target), REQ-USR-084 (`429`).

## Current system and relevant flows

A request enters `createApp()` (EVID-001) through helmet → CORS (single configured origin) → morgan → `express.json({ limit: '1mb' })` → `express.urlencoded`. `GET /api/health` is answered inline. Two routers are mounted under `/api`: `directoryRouter` (`/contacts`, `/employees`) and `eventRouter` (`/events` plus `/events/:id` for PATCH and DELETE). Anything unmatched reaches `notFoundHandler`, which emits the `NOT_FOUND` envelope without reflecting the path, and any thrown or rejected value reaches `errorMiddleware`.

Inside a feature module the flow is uniform: the controller calls `validate(schema, req.query|req.params|req.body)` (`server/src/shared/http/validate.ts:18-26`), which returns a parsed value or throws a `VALIDATION_ERROR` `HttpError`; the service performs persistence work and throws typed `HttpError`s for domain failures; a mapper function projects stored documents onto an explicitly named response shape so persistence metadata cannot leak (EVID-006). Reads use `.select(...).sort(...).limit(...).lean()`; writes use load-merge-save so the model's `pre('validate')` invariant hook actually fires (EVID-007, EVID-026). Controllers are `async` and unwrapped — Express 5 forwards rejections to the single error handler.

There is no authentication middleware, no `users` collection or model, and no audit collection. `env.ts` exposes only `NODE_ENV`, `PORT`, `DB_HOST`, and `CORS_ORIGIN` (EVID-027), so there is no configuration slot for operator identity today.

## Findings

### Contracts and observable behavior

- **F-001 [Verified]** No `users` model, route, schema, service, or seed data exists; the only references to `users` in server source are comments asserting the collection is deliberately untouched, plus a seed test that asserts `users` stays empty (EVID-001, EVID-008). This change is greenfield on the server.
- **F-003 [Verified]** The shared failure contract admits exactly four codes with a fixed code→status map and an envelope of exactly `code` and `message` (EVID-004); the main spec states that shape normatively and a foundation test asserts the exact key set of both the body and `body.error` (EVID-010, `server/src/test/api-foundation.test.ts:146-147,173-174`). The PRD needs at least `EMAIL_ALREADY_EXISTS`, `EMAIL_TAKEN_BY_ARCHIVED_USER`, `USER_VERSION_CONFLICT`, `USER_ARCHIVED`, `CANNOT_ARCHIVE_SELF`, `CANNOT_ARCHIVE_LAST_ADMINISTRATIVE_USER`, `NO_CHANGES_SUBMITTED`, `UNKNOWN_FIELD` (REQ-USR-058, 059, 060, 061, 062, 067, 068, 006), a `field` member, and statuses 401/403/429 that no code path can currently produce.
- **F-004 [Verified]** `api-foundation` requires a successful collection read to be an object with one named array and forbids any shared wrapper (EVID-010). `{ items, pagination }` (REQ-USR-020) is a different contract, so the change amends that requirement rather than merely extending it.
- **F-005 [Verified]** With `express.json()` at its default type (EVID-011) and `type-is` behavior confirmed by execution (EVID-012), a request carrying `Content-Type: application/merge-patch+json` is not parsed and `req.body` is left `undefined`. The observable result is a `400 VALIDATION_ERROR` about a missing body rather than the PRD's field-level semantics — a silent contract mismatch for any client that follows REQ-USR-055 literally.
- **F-006 [Verified]** `validate()` maps every Zod failure to the single code `VALIDATION_ERROR` (`server/src/shared/http/validate.ts:18-26`), and its message is `z.prettifyError(...)` output. Distinguishing `UNKNOWN_FIELD` from an ordinary invalid value (REQ-USR-059 vs REQ-USR-050) therefore cannot come from the current helper unchanged.
- **F-007 [Verified]** `z.strictObject` already gives the repository a rejection-not-stripping behavior for unknown query keys (`server/src/modules/directory/directory.schema.ts:33-46`), and `event.schema.ts:107-119` already relies on absent optional keys not appearing in the parsed object (`Object.keys(patch).length > 0`). Both mechanisms the PRD needs — `UNKNOWN_FIELD` and `NO_CHANGES_SUBMITTED` — are expressible with the installed Zod 4.4.3; only their error-code mapping is missing.
- **F-008 [Verified]** `DELETE → 204 no body` and `404` for a well-formed but unknown id are already the house contract (EVID-010, `server/src/modules/events/event.controller.ts:59-64`), so REQ-USR-069 fits without a contract change. Archive idempotency (REQ-USR-070) differs from the events precedent, which returns `404` when nothing was deleted.
- **F-009 [Verified]** ISO-8601-UTC on the wire (REQ-USR-040) matches the existing mapper convention (`event.service.ts:236-237` emits `toISOString()`), so no new date policy is needed — only consistent application to `lastLoginAt`, `archivedAt`, `createdAt`, `updatedAt`.

### Data and invariants

- **F-010 [Verified]** MongoDB sorts `null` and missing fields *before* all values in ascending order (EVID-013). REQ-USR-025's `NULLS LAST` for `lastLoginAt` ascending is therefore not achievable with `sort({ lastLoginAt: 1 })`; it requires either a computed presence key sorted before the value, or a persisted derived field.
- **F-011 [Verified/Inference]** REQ-USR-024 fixes ascending status order as `active, inactive, blocked`, which is neither the lexical order of those strings (`active, blocked, inactive`) nor derivable from any collation (EVID-014 — collation reorders characters, not domain semantics). A rank must be materialized somewhere: in the pipeline via `$addFields`, or persisted on the document.
- **F-012 [Verified]** `$regex` "is not collation-aware" and cannot use case-insensitive indexes (EVID-016), and collation's supported-operation list excludes it (EVID-014). A single query cannot both collate names and regex-search them under one collation.
- **F-013 [Verified]** Under PCRE2 (MongoDB 6.1+), the `i` option is ASCII-oriented; UTF-8-aware matching requires the `(*UCP)` verb (EVID-016). "Case-insensitive where applicable" (REQ-USR-027) combined with Cyrillic support (REQ-USR-026) is therefore not delivered by copying the existing `$options: 'i'` pattern (EVID-006). Note this also means the current directory search has the same latent limitation — relevant as precedent, not as a defect this change must fix.
- **F-014 [Verified]** The house search shape is `$or: [{firstName: /x/i}, {lastName: /x/i}]` (EVID-006). No value of `x` equal to `anna smith` matches a document whose `firstName` is `Anna` and `lastName` is `Smith`, so `AC-USR-007` fails by construction unless full-name search is defined against a combined stored value or a tokenized query.
- **F-015 [Verified]** Nothing in the repository enforces email uniqueness: both directory models deliberately declare no unique index (EVID-008). REQ-USR-005/006 need a unique normalized-email constraint spanning archived records, which is new persistence behavior, and creating it on a collection with pre-existing duplicates fails — the same class of precondition the archived change tracked as a manual step (EVID-026).
- **F-016 [Verified]** Every existing model sets `versionKey: false` and the main specs forbid exposing persistence metadata (EVID-007, EVID-008, EVID-010). REQ-USR-048 requires a `version` number in the detail DTO and REQ-USR-039 requires it absent from the list DTO — so `version` is a *domain* field here, not incidental persistence metadata, and that distinction must be stated deliberately.
- **F-017 [Verified]** Mongoose's built-in optimistic concurrency is off by default and requires a `versionKey` (EVID-017), signalling conflicts as `VersionError` from `save()` (EVID-018). Using it would reintroduce a version key on the document; not using it means the version guard must be part of the write's own filter, which conflicts with the load-merge-save convention (EVID-007) unless the guard is expressed as a conditional update.
- **F-018 [Inference, from EVID-005 and EVID-008]** With a unique index in place, a losing concurrent write raises a driver `E11000` error, which is not an `HttpError` and therefore collapses to `500 INTERNAL_ERROR` unless explicitly mapped. A check-then-write uniqueness test alone cannot satisfy REQ-USR-062 under concurrency (R-004).
- **F-019 [Verified]** REQ-USR-006 requires distinguishing "email owned by an active user" from "email owned by an archived user" (`EMAIL_ALREADY_EXISTS` vs `EMAIL_TAKEN_BY_ARCHIVED_USER`), which a duplicate-key error alone does not tell you — the owner's `archivedAt` must be read to choose the code. This is a two-step conflict resolution, not a one-step mapping.
- **F-020 [Verified]** No phone-parsing dependency exists (EVID-019); `libphonenumber-js` 1.13.11 is MIT with no production dependencies (EVID-020). REQ-USR-030's "SHOULD" makes the dependency a proposal-level choice, and REQ-USR-031 requires a deployment default region that has no source in the system today (U-003).
- **F-021 [Verified]** Phone search (REQ-USR-033) requires normalizing both sides; since stored E.164 and a formatted query differ textually, matching depends on a stored normalized/digits form — the same derived-key conclusion as F-010, F-011, and F-014.
- **F-024 [Inference, from EVID-025]** Tests run against a standalone in-memory MongoDB, and standalone deployments do not support multi-document transactions. Any audit-plus-mutation design (REQ-USR-081) that assumes cross-collection atomicity would be unverifiable in the current test environment, and the production topology is unknown (U-004).

### External contracts

Resolved from this workspace: express 5.2.1 (with body-parser 2.3.0, type-is 2.1.0), mongoose 9.9.1, zod 4.4.3, helmet 8.3.0, mongodb-memory-server 11.2.0, TypeScript 6.0.3 targeting ES2023 (`server/tsconfig.json`).

- **RFC 7396 (JSON Merge Patch)** — the PRD's semantics in REQ-USR-056/057 (omitted = unchanged, `null` = remove, nested objects merge recursively, `{}` = no-op) match the RFC. Two PRD rules go beyond it: rejecting unknown members (REQ-USR-059) and requiring a non-patch `version` member inside the patch document (REQ-USR-060). The result is merge-patch-*like*, and later artifacts should describe it as such rather than claiming pure RFC 7396 conformance. The recommended `application/merge-patch+json` media type interacts with F-005.
- **MongoDB** — collation applies to `find`/`aggregate`/`createIndex`/`count` but not `$regex` (EVID-014, EVID-016); `null` sorts first ascending (EVID-013); aggregation `$sort` uses an index only as the first stage or after only `$match`, with a 100 MB in-memory threshold (EVID-015). Together these mean a single query cannot simultaneously be index-served, collation-correct for Cyrillic names, and ordered by a computed status rank with nulls last — unless the ordering keys are persisted rather than computed.
- **Mongoose 9.9.1** — `optimisticConcurrency` is off by default and requires a `versionKey` (EVID-017); document `validate` middleware does not run on query updates and `runValidators` defaults to off (EVID-026). Any invariant enforced only in a `pre('validate')` hook is bypassed by `findOneAndUpdate`.
- **libphonenumber-js 1.13.11** — MIT, dependency-free (EVID-020). Not installed today.

## Options and research-informed direction

| Direction | Evidence-supported benefits | Costs and risks | Reversibility |
| --- | --- | --- | --- |
| A. Persist derived sort/search keys (`emailNormalized`, normalized name and full-name keys, phone digits, numeric status rank) and serve list reads with `find().sort().collation()` plus indexes | Every required ordering (F-010, F-011) and search case (F-013, F-014, F-021) becomes index-servable; keeps the read shape close to the existing directory pattern (EVID-006); supports the <500 ms target (REQ-USR-082) | Derived keys must be recomputed on every write path or they silently rot; more schema surface; collation choice becomes a persisted decision tied to the index | Medium — keys are additive, but an index with a collation cannot be altered in place |
| B. Compute ranking in an aggregation pipeline (`$match` → `$addFields` → `$sort` → `$facet`) with a collation option | No derived state to keep in sync; ordering rules live in one readable place; `$facet` yields items and total in one round trip | `$sort` after `$addFields` cannot use an index (EVID-015), so the whole filtered set is sorted in memory under a 100 MB ceiling; `$regex` still is not collation-aware (F-012) | High — pipeline is code-only |
| C. Mongoose built-in optimistic concurrency (`optimisticConcurrency: true` with a renamed `versionKey`) | Conflict detection is atomic and library-maintained (EVID-017, EVID-018); works with the house load-merge-save write path (EVID-007) | Re-introduces a version key the house style removed everywhere (F-016); `VersionError` must be translated to `USER_VERSION_CONFLICT`; version increments on *any* save, including archive, which REQ-USR-071 deliberately keeps version-free | Medium |
| D. Explicit domain `version` guarded by a conditional `findOneAndUpdate({ _id, archivedAt: null, version })` | One atomic write covers archived-state and version in a single filter; `version` is honestly a domain field (F-016); archive stays version-free | Query updates bypass document validation and `pre('validate')` hooks (EVID-026), so all invariants must be enforced before the write; a `null` result is ambiguous (missing vs archived vs stale) and needs a disambiguating read to choose among `404`, `USER_ARCHIVED`, `USER_VERSION_CONFLICT` | Medium |
| F. Defer the requirements that depend on absent systems (self-archive protection, last-administrative-user, audit trail, 401/403/429) | Ships the four endpoints against verified ground; avoids fabricating an authorization model the PRD explicitly defers to another document (§90) | The PRD marks several of these MUST; deferral must be an explicit, visible scope decision, not an omission | High |

### Recommended direction

Build `users` as a self-contained module following the existing module anatomy (F-025), and let the *data model carry the ordering and matching semantics* rather than the query: persisted normalized keys plus a persisted status rank (Direction A), with the aggregation approach (B) reserved for the total count or for orderings that later prove too rare to index. This is the only option that satisfies REQ-USR-022 to REQ-USR-027 simultaneously without an unbounded in-memory sort, given F-010 through F-014.

For mutation, prefer an atomic conditional write whose filter carries the whole precondition — identifier, archived state, and version (Direction D) — because REQ-USR-060 and REQ-USR-061 are conditions on the same write, and evaluating them in application code between a read and a save reintroduces exactly the lost-update the requirement exists to prevent. The accepted cost is that document middleware will not run (EVID-026), so validation and normalization must be complete before the write is issued, and the "no document matched" outcome must be disambiguated deliberately. Direction C remains a legitimate alternative if the project prefers library-owned concurrency; the decision belongs to design (D-003).

Treat the requirements that cannot be honestly implemented without authorization — REQ-USR-067, REQ-USR-068, the `401`/`403` rows of REQ-USR-073, and the audit trail of REQ-USR-081 — as scope decisions the proposal states out loud (Direction F), not as silently missing behavior.

Boundaries the recommendation does not settle: whether `users` may hold personal data at all (D-001), whether the shared envelope and collection-response contracts are amended or a users-specific contract is carved out (D-002), and whether a phone parser is added now (D-004).
